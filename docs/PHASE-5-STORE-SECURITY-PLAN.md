# Phase 5：商店反馈与安全收口计划

状态：S1 第一轮完成，实施分支：`codex/phase-5-store-security`

Phase 4 已完成运行时基础、诊断能力、发布包和隐私政策，当前版本已经提交 Chrome Web Store 审核。Phase 5 不再继续堆叠功能，先处理审核反馈、真实用户反馈和敏感数据边界。

本轮先完成低风险边界收口：共享规则导入不再接受填充/选择值，日志查询和清空限制在 Panel，日志批次限制在顶层 Content Runtime，旧版迁移键在迁移后清理；不引入自制加密。

## 目标

- 快速响应 Chrome Web Store 审核意见，不改变已发布版本的行为承诺。
- 把真实页面运行日志转化为可复现的回归测试。
- 明确密码和完整备份的本地安全边界，避免隐私政策与实现不一致。
- 保持规则执行的停止、取消、导航隔离和诊断能力稳定。

## 实施顺序

### S0：审核与发布反馈

- 记录审核意见、拒审原因或用户报告，并为每条反馈建立最小复现。
- 只修复可复现问题；不因猜测增加权限或扩大数据收集。
- 修复后更新版本号、安装包、变更记录和隐私政策中的实际行为说明。

### S1：敏感数据边界评估

- 盘点规则值、完整备份、剪贴板和运行日志的所有存储/传递路径。
- 明确 Chrome 本地存储不是密码管理器，评估是否需要系统级安全存储或改为用户每次输入。
- 对非目标网站、错误 frame、伪造消息、错误 profile 和旧 revision 继续做负向测试。
- 不引入“自制加密”作为安全承诺；没有可靠密钥管理时，宁可保持本地优先并明确限制。

### S2：运行时回归与诊断

- 用无痕 Chrome 验证页面加载、条件触发、刷新终止动作和多规则串行执行。
- 验证 `documentId`、刷新 pending、BFCache、SPA 路由和配置更新之间不会产生旧流程副作用。
- 日志继续保持脱敏，并能关联 `profileId`、`runId`、`stepId`、重置原因和最终状态。
- 把用户提供的真实问题先转成虚拟数据夹具，再提交测试。

### S3：小步功能扩展

只有 S0–S2 稳定后，才评估以下能力：

- 更多内置 Action，例如键盘操作或聚焦；
- 条件组合和更明确的触发边界；
- 规则模板与变量复用；
- 可选的执行结果验证，而不是仅判断步骤是否执行完成。

暂不做云同步、第三方脚本市场、任意表达式、跨域 iframe 自动化和复杂 DAG；这些能力会显著扩大权限、安全和维护边界。

## 验收门槛

- 每个审核/用户问题都有复现步骤、修复提交和回归测试。
- 无真实密码、Cookie、MFA 或完整备份进入仓库、测试夹具或日志。
- 规则启停、刷新、导航和配置变更后，旧运行不能继续修改页面。
- 隐私政策、Chrome Web Store 数据披露、manifest 权限和实际代码保持一致。
- 发布包可以从当前源码重新生成，版本号、manifest 和 Git tag 一致。
